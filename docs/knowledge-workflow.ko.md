# DEVONthink와 에이전트로 오래 쓰는 지식 저장소 만들기

2026-09-08 기준 제안입니다. 아래 구조는 이 프로젝트의 운영 제안이며 DEVONtechnologies가 정한 표준은 아닙니다. 실제 DB를 자동으로 재편하거나 기존 자료를 이동하지 않습니다.

## DB는 자료의 소유와 사용 범위로 나누기

DB를 주제마다 만들면 한 질문에 필요한 자료가 여러 곳으로 흩어집니다. 먼저 업무·개인·공통 참고자료처럼 보관 책임, 접근 권한, 보관 기간이 다른 경계를 나누고, 주제는 DB 안에서 표현하는 구성이 적합합니다.

| DB 예시 | 보관 대상 | 분리하거나 합칠 기준 |
| --- | --- | --- |
| Personal | 생활 기록, 개인 계획, 배움에서 얻은 판단 | 다른 사람과 공유할 업무 자료와 구분 |
| Work | 현재 업무, 프로젝트 결과, 회의 근거 | 회사·고객별 권한이나 반출 조건이 다르면 별도 DB |
| Library | 논문, 책 메모, 기술 자료, 다시 참고할 공개 정보 | 여러 프로젝트가 함께 참조할 수 있는 자료 |
| Archive | 종료된 활동 중 장기 보존할 자료 | 자주 닫아 두거나 별도 보관할 실질적 이유가 있을 때만 추가 |

이미 쓰는 DB가 있다면 먼저 그 역할을 문장 하나로 정의합니다. 새 이름에 맞추려고 전체를 옮길 필요는 없습니다. 연도별 DB도 실제 보관·동기화·성능 요구가 생겼을 때 나눕니다. 열린 DB 자동 연결 모드에서는 DB를 나누는 것만으로 AI 접근이 차단되지는 않습니다. 특정 DB 제외 설정이나 `mcp-private`을 사용합니다.

## 물리적 그룹은 얕게, 여러 관점은 태그와 스마트 그룹으로

다음은 한 DB 안의 출발점입니다. 그룹을 미리 모두 만들지 말고 실제 자료가 생길 때 추가합니다.

```text
00 Inbox          아직 처리하지 않은 자료
10 Projects       끝나는 조건이 있는 현재 활동
20 Areas          계속 관리하는 생활·업무 영역
30 Reference      다시 찾아볼 근거와 참고자료
90 Archive        종료됐지만 보존하는 활동
```

Inbox는 대기열로 사용합니다. 모든 자료를 영구히 쌓아 두는 위치가 되면 검토할 항목을 구분하기 어렵습니다. 기본 보관 위치를 먼저 정하고, 같은 자료가 여러 프로젝트에 필요할 때 원본 링크 또는 같은 DB 안의 Replicant를 사용합니다. Replicant는 같은 내용과 UUID를 공유하므로 한 곳의 본문 수정이 다른 인스턴스에도 반영됩니다.

태그는 소수의 반복되는 구분부터 시작합니다. 예를 들어 `검토대기`, `근거확인`, `탄소회계`처럼 상태나 주제를 표현할 수 있습니다. 태그 목록과 뜻을 한 메모에 적고 에이전트가 매번 동의어를 새로 만들지 않게 합니다. 날짜가 불명확한 문서에는 파일 수정일을 작성일로 단정해 붙이지 않습니다.

**DEVONthink의 그룹 태그는 일반 태그와 동작이 다릅니다.** 기존 그룹 이름에 해당하는 태그를 추가하면 그 그룹에 Replicant가 생길 수 있습니다. 문서를 그룹 밖으로 옮기면 해당 그룹 태그가 사라지는 동작도 있습니다. 이름만 보고 일반 태그로 처리하지 말고 DB·그룹의 태그 설정부터 확인해야 합니다. [DEVONthink 3 태그 도움말](https://download.devontechnologies.com/download/devonthink/3.8.2/DEVONthink.help/Contents/Resources/pgs/gettingstarted-tagging.html), [공식 태그 옵션 설명](https://www.devontechnologies.com/blog/20211019-devonthink-tag-options).

스마트 그룹은 저장해 둔 조건에 맞는 자료를 모아 보는 용도로 사용합니다. 실제 보관 위치와 별개로 ‘검토 대기’, ‘특정 주제’, ‘최근 추가 자료’를 볼 수 있습니다. 이 서버는 기존 스마트 그룹의 항목을 탐색할 수 있으며, 스마트 그룹 생성·조건 수정은 현재 DEVONthink UI에서 수행합니다. 구체적인 조건은 사용하는 버전의 UI에서 확인합니다.

## 에이전트가 맡을 일

1. `dt3_databases`로 현재 접근 가능한 DB와 루트를 확인합니다. 여러 DB가 관련되면 각각 네이티브 검색을 하고 출처의 DB UUID를 유지합니다.
2. 그룹을 페이지 단위로 탐색하고 UUID로 중복을 제거합니다. 큰 가져오기가 진행 중이면 목록이 변할 수 있으므로 시점과 누락 가능성을 기록합니다.
3. 관련 문서만 읽고, 분류 제안·유사 문서·중복 후보·참조 링크를 조회합니다. DEVONthink의 분류 점수는 정답이 아니라 검토 근거로 사용합니다.
4. 한 번에 약 10~20건의 이름·태그·보관 위치 변경안을 제시합니다. 기존 위치, 제안 위치, 이유, 원본 링크를 함께 적습니다. 이 수량은 운영 제안이며 서버의 강제 제한은 아닙니다.
5. 허용된 변경만 최신 revision으로 미리보기한 뒤 적용하고 결과를 다시 읽습니다. 다른 Replicant가 유지되는지도 확인합니다.
6. 변경 전후, 성공·실패·미확인 항목을 짧은 작업 메모에 남깁니다. 중단 후에는 이 기록과 실제 상태를 대조합니다. 서버의 메모리 내 요청 영수증은 장기 작업 이력이나 자동 복구 장치가 아닙니다.

개인적인 판단과 원문 사실은 구분합니다. 요약 메모에는 질문, 현재 결론, 근거 링크, 상충하는 자료, 확인 날짜를 남깁니다. 원본은 DEVONthink에 두고 Git에는 작은 지식 페이지와 출처를 유지하면 대용량 원본을 저장소마다 복제하지 않아도 됩니다.

## 그대로 사용할 요청 예시

### 첫 구조 조사

> 열린 DB의 역할과 상위 그룹 구조를 읽고, 현재 구성을 설명해줘. 기존 DB를 옮기지 말고 보관 범위가 겹치는 곳, Inbox에 남은 자료, 정리가 필요한 그룹을 근거 링크와 함께 제안해줘. 전체를 못 봤으면 조사한 범위를 명시해줘.

### 프로젝트 정리

> 이 그룹에서 최대 20개 문서를 조사하고 DEVONthink의 분류 제안을 참고해 이름·태그·위치를 정리할 안을 만들어줘. 그룹 태그와 Replicant를 확인하고 기존 태그를 보존해줘. 변경 전후와 근거를 먼저 보여줘.

### 배움을 지식으로 남기기

> 여러 DB에서 이 주제와 관련된 자료를 찾아 비교해줘. 내 판단과 원문 주장을 구분하고, 반대 근거와 미확인 부분도 적어줘. 원본 링크가 있는 짧은 지식 메모를 작성해줘.

### 정기 점검

> 지난 검토 이후의 Inbox와 진행 중인 프로젝트를 확인해줘. 끝난 활동, 검토되지 않은 자료, 출처가 없는 요약을 찾아 다음에 처리할 항목만 보여줘. 중복 자료는 삭제하지 말고 후보로 표시해줘.

정기 점검은 사용자가 필요할 때 이 요청을 실행하는 방식으로 시작합니다. 자동 예약은 별도로 설정하지 않습니다. 사용량과 실제 반복 작업이 확인되면 스케줄러에 같은 절차를 연결할 수 있습니다.

## 현재 기능과 다음 확장 구분

| 기능 | 현재 상태 | 확장할 조건 |
| --- | --- | --- |
| 여러 DB 연결·열린 DB 추적 | 구현, 실제 DB 개폐 검증 | DB별 정책이 다르면 별도 클라이언트 설정 사용 |
| 네이티브 검색·분류·유사도·참조 | 구현 | 검색 품질은 실제 자료로 평가 |
| 같은 DB 안의 생성·수정·이동·Replicant | 구현, 미리보기·revision 확인 | 대규모 작업 전 영속 작업 이력과 복구 절차 필요 |
| 닫힌 DB 열기·새 DB 생성 | 앱 UI에서 수행 | 허용 경로·접근 범위·백업 규칙을 정한 뒤 MCP 도구 검토 |
| 스마트 그룹·스마트 규칙 생성 | 앱 UI에서 수행 | DEVONthink 3 스크립팅 사전과 실제 동작을 검증한 후 추가 |
| 사용자 정의 메타데이터 쓰기 | 현재 읽기만 지원 | 사용 중인 필드와 자료형이 정해지면 구현 |
| OCR·음성 전사·파일 변환 | 현재 도구에 없음 | DEVONthink 에디션과 실제 입력 형식별 지원을 검증 |
| DB 간 이동·중복 삭제 | 현재 도구에 없음 | 출처 링크, 복제 관계, 백업·복구를 보장한 뒤 검토 |

독립 검색 인덱스나 벡터 DB는 현재 추가하지 않습니다. 먼저 DEVONthink의 검색과 분류로 실제 질문을 해결하고, 반복적으로 해결되지 않는 검색 사례가 쌓이면 그때 보완 수단을 평가합니다.
